# Spore server

Indexer + JSON API for the pump.fun family tree (coins quoted in other pump coins, `depth ≥ 1`,
plus every ancestor down to depth 0). Node 25 ESM, `express`, `node:sqlite`; no native modules, no
keys. The browser builds and signs every transaction itself; this process only reads the chain,
serves JSON, proxies an allow-listed JSON-RPC subset and publishes token metadata to our own host.

Spore is a launchpad (DESIGN §11): by default the API shows only coins spawned through it ("ours"),
charges a launch fee at spawn and hosts metadata itself (pump.fun's IPFS upload is gone).

```
npm start                       # production: BACKFILL on, serves ../web/dist if built
npm run dev                     # --backfill-limit=150 (= BACKFILL_LIMIT=150): a bounded backfill that finishes in ~1 min on the public RPC
npm test                        # node --test (SPORE_NET=0 skips the mainnet smoke test)
npm run fixtures                # re-capture test/fixtures from mainnet (read-only)
```

## How the index is built

**Backfill (once, resumable).** `getProgramAccounts` on the pump program with two memcmp filters
(`BondingCurve` discriminator at 0, `depth` at offset 141) for every depth `1..Global.maxCurveDepth`
returns every curve with full data (12 227 depth-1 and 184 depth-2 curves on 2026-10-18, ~4.7 s per
call on the public RPC). The rows go to the `backfill_curves` staging table. A curve does not store its
mint, so each is resolved with `getTokenAccountsByOwner(curve)` (Token-2022 first, SPL Token as the
fallback for older coins): the token account whose mint is not the curve's `quote_mint` is the coin.
Resolution order is graduated curves first, then by `realQuoteReserves`, then deeper first, so the
leaderboard fills with the big ones. A resolved child also identifies its parent's curve for free
(`bondingCurvePda(quote_mint)`), so many depth-1 curves never need their own lookup. Progress is
persisted per curve; a restart continues where it stopped and rescans at most once a day.
Then every ancestor chain is walked (`quote_mint` → curve, batched 100 per `getMultipleAccounts`)
so each tracked coin reaches a depth-0 root, mint accounts are read for decimals / token program /
Token-2022 metadata (Metaplex PDA for SPL mints), pools and vault balances are read for migrated
coins, fee-sharing configs for depth ≥ 1, and finally creation times (oldest signature on the curve;
coins with more than 4 000 transactions keep `createdAt: null`).

Cost: one `getTokenAccountsByOwner` per curve (two for the rare SPL-Token coin), plus one request per
100 coins for every batched step and one `getSignaturesForAddress` per coin for the creation-time
probe. Measured on 2026-10-18: both `getProgramAccounts` scans take ~4.5 s each; on the public RPC the
resolve step ran at **0.8 curves/s** (the per-method cap is 4/s and the IP was shared with other
processes, so 429 pauses dominated), which puts the full 12.4k-curve tree at **3–4 hours**, about an
hour if the budget is yours alone; `BACKFILL_LIMIT=150` finishes in under two minutes. On Helius or
any paid RPC (`RPC_RPS=40`, `CONCURRENCY=8`) the whole backfill, creation-time probe included, takes
**5–10 minutes**. It is resumable at every step: a restart after the limit was reached re-reports
"done" in well under a second from sqlite.

**Live.** `logsSubscribe({ mentions: [pump] })` over `WS_URL`. Every `Program data:` line is matched by
its 8-byte discriminator: `CreateEvent` with `depth ≥ 1` inserts the child (and pulls an unknown
parent chain), `TradeEvent` for a tracked mint updates reserves and records a trade, `CompleteEvent`
marks the curve complete, and pump-amm `BuyEvent` / `SellEvent` keep graduated coins' pool reserves
and trades current. The socket reconnects with backoff (1→30 s) and a silent socket is reopened
after 60 s; every (re)connect triggers a refresh.

**Refresh.** Each tick re-reads curves touched by live events or API views in the last two minutes,
plus a rolling slice sized so the whole set cycles once per `FULL_REFRESH_MS`; migrated coins get
their vault balances; SOL/USD comes from CoinGecko every 60 s (last value kept on failure).

**Pricing.** `priceQuote` = quote per token (curve: virtual reserves; pool: vault balances), scaled by
decimals. `priceSol` multiplies `priceQuote` up the chain to a SOL-quoted root; a USDC root gives
`priceUsd` directly (`priceSol = priceUsd / solUsd`); a root quoted in PUMP is priced through
PUMP's CoinGecko price (fetched with SOL's, every 60 s); any other listed quote mint (tokenized
stocks) prices as `null`.
`lockedQuote` is the sum over direct children of their raised parent tokens (curve
`realQuoteReserves`, or the pool's quote vault once migrated), in the parent's raw units;
`lockedUsd` applies the parent's own `priceUsd`.

## "Ours only" mode (DESIGN §11.1)

A coin is **ours** when its on-chain fee-sharing config (pump-fees) pays `PLATFORM_WALLET` at least
`PLATFORM_MIN_BPS` (the platform slice of `SPLIT_BPS`, 50% by default), which is what the Spawn page
writes in the create transaction. Merely naming the platform is not enough: the config is written by
the creator, and a 1 bps share would otherwise buy a permanent listing.

For the first minutes a spawn may instead be **pending**: the UI reports it with
`POST /api/spawned { mint, sig }` and the server **verifies the transaction on-chain** before
believing it (`lib/spawned.mjs`): `getTransaction(sig)` must succeed without error and carry a pump
`CreateEvent` whose mint is the reported one, whose creator is a wallet (a program-derived creator is
a holder-reward coin, which the split cannot apply to), and the platform wallet's balance must have
grown by at least the launch fee (`LAUNCH_FEE_SOL`; skipped when the fee is 0 or the platform launched
the coin itself). Anything else is a 400 (`404 { retryAfter: 3 }` while the RPC has not seen the
signature yet); a verdict is cached per signature, so the UI's retry and any replay cost no RPC.
A verified spawn is stored pending with a timestamp and the fee it paid (persisted in `kv`, bounded
to 500 entries, so a restart keeps it), the coin is inserted from its own CreateEvent (roots included:
the launch tab defaults to a SOL-quoted root, which the live path ignores as a non-spawn), tracked,
its sharing config read immediately, and it is kept hot. The indexer re-reads the sharing config of
every pending mint and of every coin younger than 30 minutes on every refresh tick (besides the 6 h
re-read for everything at depth ≥ 1); a config paying the platform its share turns the flag into
`ours`, and a pending flag older than 10 minutes without confirmation is dropped (a genuine split
lands within seconds of the create). `Coin.feePaid` (lamports as a string, or `null`) is what the
verified create paid.

Every `Coin`, `CoinRef` and map node carries `ours` and `oursPending`. With `SHOW=ours`:

- `/api/feed`: our coins (ours or pending), roots included.
- `/api/roots` and `/api/map`: the depth-0 ancestors of our coins, one row per root; `children` = direct children in scope, `descendants` = our coins below, `lockedQuote/lockedUsd` over our direct children.
- `/api/tree` and the `children` of `/api/coin`: only in-scope coins (ours + their ancestors); `otherChildren` is how many direct children on pump.fun were left out (also on `Coin`).
- `/api/candles`: 404 for a coin outside the scope.
- `/api/stats`: `coins`/`byDepth` over our coins, `roots` as above, plus `mode`, `ourCoins`, `otherChildren`.
- `/api/search`, `/api/eligibility` and `/api/coin` itself stay global: anyone may spawn under any pump coin, and a foreign coin's page opens (with no children listed).
- SSE `coin` events are sent only for our coins.

`SHOW=all` serves the whole tree; `mode`/`ourCoins` are still reported and `otherChildren` is 0.

## The map shows everything, live (DESIGN §11.5)

The Map page draws the whole custom-pair ecosystem whatever the listing mode, and must not re-request
it on every open. Server side:

**Full forest.** `GET /api/map?scope=all&limit=all[&depth=2]` → `{ roots: MapNode[], scope: "all",
version, generatedAt, total }` with every root and every descendant (`MapNode = { coin: MapCoin,
children }`, `MapCoin` = `CoinRef` + `ours/oursPending`, `mcapUsd`, `lockedUsd`, `children`,
`descendants`, `migrated`, `createdAt`), no fan-out cap, roots and children ordered by locked value.
`depth` defaults to the program's current depth cap (2) so nothing is left out. Built from `mapRef`
only (no `view()`: no ancestor walk, no volume join) from the precomputed children index; cached per
model version and at most once per 10 s, together with its JSON, gzip and brotli bytes, so a burst of
opens shares one build. Measured on the production copy (15 575 nodes, 2 145 roots): ~50 ms tree
walk + ~65 ms encode on a warm process, 5 MB JSON / 1.1 MB gzip; the response carries
`x-map-build-ms` / `x-map-encode-ms` and `/api/health.map` keeps `lastBuildMs`/`maxBuildMs`.
`limit=<n>` (default 60, fan-out 40) and the ours-mode default are unchanged.

**Delta sync.** Every coin row carries `updated_at` in **milliseconds** (schema v3 multiplies the old
seconds once; `Coin.updatedAt` on the coin page stays in seconds). It moves only when something a map
node shows changed: a new coin, reserves / complete / migrate / pool balances (trades and refresh
ticks), a sharing config (`ours`), a pending flag, an on-chain name/ticker/uri that resolved, or an
off-chain image that resolved (the `meta` row's image changed → every coin behind that uri is stamped
through the uri → mints index). A child's reserve/migration change also stamps its parent (locked
value, child count). A refresh tick that re-reads an identical curve stamps nothing. Stamps are kept
strictly after the last full build (`generatedAt`), so a change landing in the same millisecond is
still caught. Not stamped: price moves inherited from an ancestor or from SOL/USD (every node would
change every minute; the client recomputes nothing and `mapdelta` carries the traded coins).
`GET /api/map?scope=all&limit=all&since=<ms>` → `{ nodes: [{ ...MapCoin, parentMint }], removed: [],
generatedAt, total, version }`: only the nodes with `updated_at > since` that the full map would draw
(a root with children, or a child whose parent chain reaches a tracked root), largest locked value
first; `removed` is reserved (coins are never deleted); `total` lets a client tell a stale cache from
a complete one. Cached 10 s per `since` value. A client keeps the full set + `generatedAt`, asks
`since=<generatedAt>` on open and merges.

**SSE `pair`** `{ coin: MapCoin, parent: MapCoin }`: every coin the live stream creates whose parent is
tracked (depth ≥ 1), in both listing modes, and again when a known child's parent becomes known
(adopt / enrich pull the ancestor chain; an on-demand, untracked parent is tracked the moment it gets
a child). Deduped per mint for 60 s. `coin` keeps its ours-only semantics.

**SSE `mapdelta`** `{ at, updated: [{ mint, mcapUsd, lockedUsd, children, descendants, migrated, name,
symbol, image }] }`: flushed every 3 s, only when something changed, from the same dirty set the
stamps feed (so a late-resolved logo or name reaches open maps), at most 500 entries per batch
(largest locked value first; the rest wait for the next flush). `trade` and `stats` are unchanged.
`/api/health.indexer.map` counts pairs and deltas sent.

**Metadata coverage** (names and logos must show). On-chain name/symbol come from the `mints` table and
ride on every node. Off-chain JSON is fetched for **every tracked coin in both modes**: `MetaFetcher`
runs a sweep at boot and every minute (in slices on the shared scheduler, `lib/sliced.mjs`, so the pass over every
coin never holds the event loop) that queues every tracked coin whose uri has no row, a stale row, or a
failed row whose backoff elapsed, ordered by locked value then recency; 6 workers; results persist in
`meta` (`attempts` counts consecutive failures: retries after 15 min, 30 min, 1 h … capped at 24 h;
a temporary failure (429, 5xx, a timeout or network error, gateways that mixed a 403/404 with any
of those, or a rotation whose gateways all did not resolve, which is our DNS) at 3 h while fewer than
5 fetches failed in a row, then on up to a day like any other; a non-IPFS host that answered 404/410
or does not resolve 5 times in a row (`dead_streak` counts that run, any other failure or a success
resets it; `attempts` counts every failure) is asked weekly, and until then on the usual backoff, so a
local DNS outage costs a few retries, not a week; `metaRetryS` in `lib/meta.mjs`; a resolved image is re-read weekly, a resolved JSON
without an image daily; a uri that once resolved keeps its image when a later re-read fails). IPFS content (`ipfs://`, any `/ipfs/<cid>` path, or
`<cid>.ipfs.<gateway>`) goes through the gateway rotation pump.mypinata.cloud → ipfs.filebase.io →
4everland.io → ipfs.io → dweb.link → gateway.pinata.cloud → w3s.link (`IPFS_GATEWAYS`). pump.fun's own
pinata gateway comes first: measured 2026-10-19 it answers in 0.2 s, 200 for everything pump.fun pinned
and a definitive 403 otherwise. ipfs.filebase.io and 4everland.io follow it (`GATEWAY_RULE` 2,
2026-11-10): that day ipfs.io, dweb.link, gateway.pinata.cloud, w3s.link and nftstorage.link answered
429 to this server on the first request, while both new gateways served every stuck CID probed
(4everland redirects to `<cidv1>.ipfs.4everland.io`). cf-ipfs.com is dead and never asked; a gateway
outside the rotation that a creator wrote into the uri is tried first, the content may only be there.
An `ipfs://` uri goes through the rotation like the others (`isFetchableMetaUri`; until 2026-11-11 the
queue skipped it, as it does every non-https uri). A 403/404/410/5xx, a 429 or a timeout from one
gateway moves to the next, and a failed rotation is stored with a per-gateway summary such as
`403 pump.mypinata.cloud; 429 ipfs.io; timeout dweb.link` as its error. A rotation in which no public
gateway looked for the file (each one paused, out of the budget, or answering 429 / 408 / 425 / a 5xx
other than 504 / a network error, while pump.fun's pinata at most said it did not pin it; a public
gateway that does not resolve is passed over, and two of the rotation's own that do not resolve are our
DNS, never a deferral) is a *deferral*, not a failed attempt (`isGatewayDeferral`). When a gateway of
that rotation answered 429 or was paused, the uri is first requeued up to 3 times 10 s apart (not when
its last failure was already a deferral); otherwise it is stored at once. A run of deferrals counts at
most 3 on `attempts`, never lowers a count that real failures earned, and waits 10, 20, then 40 min
plus up to half of that as a jitter fixed per uri, so at most an hour. A rotation in which a public
gateway looked (a timeout, a 504, an answer) is stored at once and keeps the backoff above: both new
gateways hang until our timeout on a CID nobody has. Each attempt has its own 10 s timeout under a
25 s budget per uri (15 s / 30 s for images); the least-busy gateway is asked first so the workers
spread over the rotation, a host's slot is taken when it is chosen (200 ms spacing per host, kept when
rotations run side by side), and a 429 pauses that host for 10 s doubling up to 2 min, or for its
`Retry-After` when that is longer (at most 15 min). A coin page or a young coin lifts its uri to the
head of the queue even when a sweep already queued it. When the rotation gains a gateway
(`GATEWAY_RULE`), the next boot gives the old rotation's failures one more try (kv `metaGatewayRule`):
every failed IPFS row with a temporary error is due at once, and the counts the old rule inflated on
deferrals come down to 3. The image proxy uses the same rotation and allowlist (`ipfs.filebase.io`,
`dweb.link`, `w3s.link` and `4everland.io` path form included; all but ipfs.filebase.io redirect). This
is HTTP to gateways only, never the RPC. `/api/health.meta` reports the coverage over tracked coins, `{ total, withMeta, withImage,
noUri, failed, queued }` (`failed` = coins whose last fetch failed), plus this process's counters
under `run: { fetched, failed, failedTransient, deferred, rateLimited, sweeps, rotated, recheck }`.

**Logo capture** (`ImageCache` in `lib/meta.mjs`, files in `DATA_DIR/img`). A logo is captured the
first time its url is seen and kept for good:

- *First sight.* `Model.setMeta` (a metadata image that is new or changed) and `setAssetIcons` call
  `model.onImage`, which `index.mjs` points at `ImageCache.enqueueThumb`: the 64 px thumbnail is made
  at once (deduplicated, at most 20k waiting, 2 at a time), before the map asks and before the host
  can die. The periodic warm pass (3 min after boot, then every 30 min, at most 20 min each) covers
  every tracked coin's logo, family tops, the biggest families' children and the coins each listed
  asset family draws first (`Model.warmImageUrls`); a pass resumes where the previous one stopped,
  across restarts too (kv `imgWarmCursor`, the next url and its position), and a pass that gets round
  the whole list starts the next one at the top.
- *Download slots.* 8 origin downloads at once; background work (first sight, warm pass) may hold at
  most 4 of them, and a freed slot goes to the most urgent waiter: a visitor's `/api/img` or
  `/api/logo-sheet` first, then first sight, then the warm pass (renders queue the same way). A
  visitor asking for a url the warm pass queued lifts that download to the front.
- *Kept for good.* A thumbnail is served whatever its age and never deleted for it: its url names the
  image (IPFS content never changes; a new logo comes with a new url). Only the `IMG_THUMB_MB` budget
  evicts, least recently served first (the file's mtime records the last serve, at most every 6 h, so
  the order survives a restart). The warm pass stops at 85 % of that budget and never evicts; first
  sight goes on to 95 % and then evicts thumbnails nobody was served (or that were made) in the last
  30 days, down to 90 % of the budget, so a new coin still gets its logo on a full disk. The 85-95 %
  band is first sight's reserve: the warm pass does not refill the room an eviction freed (when both
  stopped at 95 % it did, and every new coin cost ~11k idle thumbnails); a capture that
  is refused all the same is counted (`freshFull`, `warmFull`) and logged at most every 10 min with
  the counts since the last warning. Originals keep their own `IMG_CACHE_MB` budget and a 24 h
  refresh; a stale original whose refresh fails is still served.
- *SVG logos* (since 2026-11-11; Backpack's stock tokens, for one, name `backpack.exchange/api/stock-logo/<SYMBOL>`,
  which answers `image/svg+xml`) are drawn into a PNG and kept as the original, served as `image/png` like
  any downloaded PNG (thumbnails and sheets as usual); SVG bytes are never stored or served, they can script on
  our origin. An SVG is what is declared `svg` or sniffed as an XML document with an `<svg>` root (plain text
  and XML types are sniffed too; a stored `Content-Encoding` gzip / deflate / br is undone first, within the
  same cap), at most 1 MB. It is fitted into 256 x 256 (aspect kept, transparent
  ground) by resvg on the image worker (`rasterizeSvg` in `lib/img-worker.mjs`), never on the event loop, and
  nothing outside the document is loaded: no system fonts (text is set in the vendored Geist faces), no
  image, stylesheet or file; scripts are not run. Before resvg sees it, a document is held to what a logo needs
  (one linear tag-level pass, references replaced as resvg reads them, so no spelling gets past it): the
  elements in `SVG_ELEMENTS` only (shapes, groups, `use`, `symbol`, `switch`, gradients, `clipPath`, `text` /
  `tspan`, `style`, title / desc / metadata; elements of other namespaces, such as editor metadata, are
  skipped by resvg and allowed), so pattern, mask, filter and `fe*`, image, foreignObject, script and marker
  are refused; every `href` must point inside the document (`#id`); no `filter` attribute or CSS property;
  at most 32 levels deep, 10,000 elements and 2,000 characters of text; plain internal entities only (no
  references or markup in them, none external or parameter, at most 64 KB of expansion). A drawing still
  running 1.5 s after the worker took it up ends that worker (the only way to stop resvg; it is no crash,
  the next job starts a fresh one; the verdict waits a turn of the loop, so an answer already in wins).
  Memory: while the worker holds a job (any op: thumbnails, sheets and cards too) the main thread samples
  the process's RSS every 10 ms, and a rise of more than 256 MB since the job began ends the worker (an SVG
  then fails for good, a thumbnail is "cannot be drawn", the jobs behind it fail once); resvg's own memory
  is capped at 384 MB besides (`lib/resvg-wasm.mjs`, the same bytes on every thread, so V8 compiles the module
  once), which holds while the loop is too busy to sample; and a worker
  that trapped in resvg or holds over 128 MB of wasm memory after a job is replaced once idle (a logo leaves
  ~10 MB). What cannot be drawn (too big, not an SVG, what a logo does not need, a parse error, no size,
  nothing drawn, past the deadline or the memory bound) is a permanent failure (`svg: …`); the worker dying
  under it is temporary until it happened twice in a row; with no worker at all it is temporary.
- *Failures are classified* and kept in sqlite (`img_fail`: url, kind, error, attempts,
  gone_attempts, next retry), so a restart does not download the dead again. Temporary (429 or every
  gateway pausing, 5xx, timeouts, network errors, IPFS gateways that mixed a no with any of those,
  every gateway or two of the rotation's own not resolving: our DNS; one rotation gateway that does
  not resolve is not enough, it may be gone for good): retried after 1 min, doubling (6 tries within the first
  hour, then on up to a day, so an unpinned CID is not asked every hour forever); a deferral (no public
  gateway looked for the file, as for metadata above) counts at most 4 in a run, never lowers a count
  real failures earned, and waits 1, 2, 4, then 8 min plus up to half of that, never the day; `/api/img` answers
  `503` with `Retry-After` (the wait left, at most 300 s) and `/api/logo-sheet` leaves the cell
  pending, however long the wait. Permanent (404/410 and the other definitive 4xx, not an image, too
  large, a lone host that did not resolve 3 times in a row: before that it is temporary, our DNS may
  be down, retried after 15 min and then 30, so the third miss comes at least 45 min after the first
  and a short local outage does not kill the logo): retried after 1 h, then a day, then weekly;
  `/api/img` answers 404 and the sheet cell is dead. `attempts` counts the failures in a row of one
  kind, so three temporary failures and then a 404 wait like a first 404 (an hour), not a fourth
  failure; a permanent failure counts the permanent failures since the last success
  (`gone_attempts` carries the count across temporary ones in between), so a url that alternates 404
  and 502 still reaches the weekly wait instead of ~330 fetches a week. A logo that downloads but
  cannot be drawn is a dead sheet cell for a week while `/api/img` keeps serving its original, and so
  is one the image worker died under twice in a row (`THUMB_CRASHES_MAX`; a render that ended with
  nothing recorded, a worker crash or an original evicted mid-render, leaves the cell pending, not
  dead); an animated webp is drawn from its first frame. Rows past their retry time by 30 days are
  forgotten. When the rotation gains a gateway (`GATEWAY_RULE`), the next boot forgets the IPFS
  failures the old rotation recorded as temporary or with a per-gateway summary (kv `imgGatewayRule`).
  When the proxy learns to draw another type (`IMG_TYPE_RULE`; 2 draws SVG), the next boot forgets, once, the
  failures an older rule recorded for it (`not an image: image/svg+xml` and the like, and `not an image:
  text/plain` / `text/xml`, which rule 1 refused before the download; kv `imgTypeRule`) and
  queues those urls for first sight, so the logos come back within seconds of the restart.

`/api/health.images` has the counters plus `thumbFiles`, `slots` (active / background / waiting per
priority), `fresh` (first-sight queue), `failing: { gone, temp, nothumb }` and `work`, the image worker's
counters (`jobs`, `failed`, `restarts`, `inline`, `overtime`, `overMemory`, `recycled`). Each worker
replacement is also logged (`img work: worker replaced (<why>)`).

**Live-path cost.** A trade used to trigger a full derived recompute (`computed()`, ≈ 90 ms at 15k
coins) because the coin's own upsert had just bumped the model version; `Model.priceOf(mint)` prices
one coin from its own chain instead, so the forest is recomputed only by consumers (API reads, the
3 s `mapdelta` flush, the 30 s stats tick). Unchanged-curve re-reads no longer bump the version either.

## Metadata host (DESIGN §11.3)

`POST /api/upload` validates like before, then `lib/metahost.mjs` writes two content-addressed files
under `META_DIR/m` (`<sha256 of the image>.<png|jpg|gif|webp>` and `<sha256 of the JSON text>.json`,
JSON shape `{ name, symbol, description, image, showName: true, createdOn, twitter?, telegram?, website? }`)
and runs `npx wrangler@3.99.0 pages deploy` for the whole directory (so earlier files stay published).
Deploys are single-flight: callers arriving during a deploy share one follow-up deploy, never two
wrangler processes at once; 240 s timeout; a failure answers 502 with the wrangler reason. The
response is `{ metadataUri, imageUri, metadata }` with `https://<PAGES_DOMAIN>/m/<hash>.json`.
The same files are served at `GET /m/<name>` (immutable, CORS `*`), and the metadata fetcher and the
image proxy resolve any `https://<PAGES_DOMAIN>/m/...` URL from the local directory before touching
the network, so coin pages work on a machine that cannot reach `*.pages.dev`.

The upload is reachable before any wallet has signed anything (the Spawn page uploads first, then
builds the transaction), so it is bounded on its own: daily quotas per client IP and globally for
bytes and deploys (`UPLOAD_DAILY_*`, 429 with `retryAfter` once spent), a ledger in sqlite
(`uploads`) of every file the endpoint wrote, and an hourly garbage collector that deletes ledger
files older than `META_GC_HOURS` that no indexed coin references (a mint's `uri` or a metadata
`image` on our host), image files only once no surviving JSON points at them (identical images share
one file). A removal triggers one deploy so the public host forgets the file too. Files written by
`tools/publish-meta.mjs` or anything else are not in the ledger and are never touched. What is not
done here: binding the upload to a wallet signature, which needs the web flow to sign a message
first (see the security notes in the fix report).

## Narrative tags (lib/narrtags.mjs)

Off by default (`NARRATIVES=on` plus a key file, §Environment). A language model reads the **public text** of a coin and
files it under a short story title ("ai bubble popping") with one of a fixed list of themes, so the Discover page can
show coins about the same thing on one card. **The grouping is a language model's reading of text that strangers wrote.
It can be wrong**: a coin can land under the wrong story, two titles can mean the same story, and a coin's creator can
write text to look like part of a story. It is context for the reader and nothing else; no number, order or alert on
the site depends on it, and nothing here says anything about a coin's price.

- **Which coins.** A coin is asked about once `NARRATIVE_MIN_BUYERS` distinct wallets bought it within the held hour and
  it has no stored answer. The Discover snapshot offers its coins (a check in memory per coin; no stored trade is read);
  coins on the stories page go first (at most 600 wait as page coins; one not on the page for 5 min waits with the
  rest). One answer per coin is stored, "none" too; a coin answered "none" is asked once more if the text of the X
  post it links arrives later, or if it was asked with a name and ticker only (its metadata had not arrived; a failed
  metadata fetch does not count as arrived) and a description arrives later. Never a third time.
- **What the model reads**, per coin, each field cleaned (no control characters, no angle brackets) and capped: name,
  ticker, description, the host and path words of its website, its X handle or search words, the handle and text of
  the X post it links when that is stored (`x_posts`, never a flagged one), the name and ticker of the coin it is priced
  in and that coin's narrative (only when that is itself a coin of the index: USDC or another plain quote asset is no
  pairing). No image, no URL, and nothing is fetched for it. Launcher boilerplate is taken out of
  the description first: "Deployed using ...", "Created on ...", "Launched on ..." and the like, followed by a launcher
  from an explicit list (its site, with or without `https://`, a path, an emoji after it; or its name, with or without
  `@`), ending the phrase. Any other site or name stays ("Powered by x.ai", "made by @someone"), and a launcher whose
  name is also a common word (bonk, bags, bloom, jupiter ...) counts only after "launched/created/deployed on/using/via".
  A description that is only boilerplate, or boilerplate plus a filler word ("Token deployed using ..."), is empty, and
  a coin left with nothing but its name and ticker (a handle, a community link or a launcher page is not text) is
  marked `no_text`. The list was not checked against how often each form occurs in stored descriptions.
- **When coins share a narrative.** A coin joins an existing narrative only when its own text points at the same
  specific story: the same event, post, person, product or running joke. Sharing a broad subject (a cat, a game, a
  politician, "ai") or a theme is not enough; different words for the same story still belong together. The coin it is
  priced in is not the coin's own text: it counts only together with it. A coin whose text names no subject (no text at all, or
  a description that is only a slogan, its own name or a chain or community phrase), priced in another coin or not,
  joins a listed narrative, or a new story that another coin of the same request starts from its own description, site
  or post, when its name or ticker carries that story's distinctive word (bubble or pop for "ai
  bubble popping", bigfoot for "trump files on bigfoot"), word forms and derivatives included ("popped", "Bubble Inu");
  a kind of thing or a name many stories share (cat, dog, inu, ai, coin, meme, trump, elon, crash, game) is never
  distinctive, and a name or ticker whose word plainly means something else (for example a known character or person of
  that name) does not join. Any other such coin gets "none" unless its name is itself widely known; a name that is only
  a shared word (Trump, Elon, Cat, AI) is "none", and such coins never start a story among themselves. When the model
  is unsure whether a coin's text points at the same story it answers "none" (a wrong grouping is worse than no
  grouping); for a coin whose text names no subject, a name or ticker that carries a story's distinctive word is not
  treated as a guess. When a description or post says what the coin is about, that decides, not the name. New titles name the story at the level a
  reader would search for it ("gta 6"), not one coin's angle on it.
- **The request**: batches of 20 coins, at most 6 requests a minute, one at a time, through the official
  `@anthropic-ai/sdk` (pinned). A batch goes when 20 coins wait or the oldest has waited 2 min (`FILL_WAIT_MS`), page
  coins included: measured live on Sonnet 5.5, sending page coins at once made requests of one or two coins that each
  paid for the whole story list (about $1.25 an hour); waiting and caching the list brought it to about $0.37 an hour.
  Each request carries the fixed instructions and themes (a cached system block), the story list (id, theme, title) as
  a cached block of its own (a snapshot of the 150 most recently used narratives, kept for 15 min, `SNAP_MS`, and
  renewed at once after a retitle, so its bytes repeat and the provider reads it from cache), the narratives made or
  used since the snapshot after it, uncached, and the coins as JSON. The answer is forced into a JSON schema; per coin
  an existing narrative's id (optionally with a wider title for it, see below), a new title and theme, or "none". No
  thinking is requested; the output allowance grows with the batch (64 tokens plus 56 a coin).
- **The server decides, not the model**: an id that was not offered is rejected, a theme outside the list becomes
  `other`, a title is cleaned (lower case, letters and digits only, 2-5 words, at most 40 characters; URLs, handles and
  emoji go; a blocked word makes it no title) and merged into an existing narrative that says the same words (case,
  punctuation, plurals, articles), an answer for a coin that was not asked about is ignored, and a reply that is not the
  expected JSON drops the whole batch. **The empty-coin guard**: a coin with no description (after the boilerplate is
  out, or one made only of the coin's own name, ticker and filler words: "Bubble Inu on Solana"), no website words and
  no post text, whether it is priced in another coin or not, is stored under a narrative
  only when that narrative's title names it by its name or ticker: a shared word that can carry a subject (3+ letters
  and not filler, a number of 2+ digits, or a two-letter word that is not a function word), a 4+ letter word inside a
  run-together name when the rest of the name is only filler or kind words, digits or a plural s ("fiona" in
  "BabyFiona"; not "last" in "Blast" or "bubble" in "Bubblegum"), or the title written without spaces ("gta 6" for "GTA6"). Whole words
  are compared without a few common English endings (`stemWord`: -s, the e of -es, -ed and -ing with a doubled
  consonant undone, so "Pop Inu" and "popped" fit "ai bubble popping" and "Foxes" fits "fox"; nothing where the base
  word is unsure, so "Pope" and "hoped" do not; a short list of words that only look like a form stays whole, so
  "wicked" is not "wick" and "herring" is not "her"; and a short word inside another, "cat" in "Catalyst", never
  did). A kind word (cat, dog, ai, trump, elon, crash, game, and common animal kinds such as hippo or frog) or a common
  English word (a short list: last, first, big, file, man, king ...) shared with a title that also has a distinctive
  word does not count, as filler (inu, coin, meme, the ...) never does: a coin named "AI", "Trumpcoin", "Hippo" or
  "Last Chance" with no text does not pass for "ai bubble popping", "trump files on bigfoot", "fiona the hippo" or
  "the last penny", and a bare "Elon" does not pass for "elon musk". The guard is the outer bound; inside it the model
  decides (a name whose word means something else, or a lone kind word against a title with nothing else, is the
  model's call). Not matched: -es after a single s ("Buses" for "bus"). Otherwise it
  is stored as "none" (`/api/health` `forcedNone`). Abbreviations (NVDA for nvidia) and names in another script than
  the title are not matched, so such a coin with no text stays "none". **The one-time retitle**: an "existing" answer
  may suggest a wider title for its narrative (a story named after its first coin's angle). It is applied at most once
  in a narrative's life (`narratives.retitled`), only when at least 2 coins of that batch were filed under it (or 1
  plus at least 2 filed before), after the same cleaning as any title, only when it drops words of the old title and
  adds none ("gta 6" for "gta 6 birdwatching feature"; one word that can carry a subject must be left), and only when
  it is not the title of another narrative (then it is ignored; narratives are never merged this way). So no reply can
  bring a new word onto a card; the price is that a widening which needs a new word is refused, and the title then
  stays narrow. The theme never changes. `/api/health` counts `retitled` and `retitleRefused` (a suggestion that only
  repeats the listed title is not counted). Coins of a failed batch are asked again in smaller batches (20, 5, 1). A coin
  that fails alone, while other requests have been answered since it first failed, is stored as given up and not
  asked again for a day. Replies that keep being unusable (refused, cut off at `max_tokens`, not JSON) are not a
  coin's doing: after three in a row the tagger pauses like after a failed request (30 s, doubling to 15 min), logs
  one line per pause, and gives up no coin; `/api/health` counts them (`malformed`, `refusals`, `cutOff`).
- **Untrusted text.** Coin text goes in as JSON strings inside a marked block and the instructions say to treat it as
  data. Whatever comes back is only ever an id we offered, a theme from our list or a cleaned title; nothing from the
  model is run, fetched or put in a URL. A coin whose text tries to steer the model is still just tagged or "none".
- **Spend.** Before a request its worst case (a high estimate of the input at the cache-write rate, all of
  `max_tokens`) is written to `narrative_spend`; the request is refused when the UTC day would pass
  `NARRATIVE_DAILY_USD`. Afterwards the row is corrected to the usage the provider reported (a failed request with an
  HTTP status is taken back; one that timed out keeps its worst case). A 429, 5xx or overloaded answer pauses all
  requests for 30 s, doubling up to 15 min (a `Retry-After` is respected); a refused key or request pauses 30 min.
  A failing provider only leaves coins untagged.
- **Themes** (fixed in code): ai, animals, politics, celebrity, market crash, tech & products, gaming, sports,
  culture & memes, finance & stocks, crypto native, world events, other.
- **Rules version.** The rules above have a version (`RULES_VERSION` in lib/narrtags.mjs, now 2; stored in sqlite as
  the `kv` row `narr_rules_version`). At startup, with the tagger on or off, a database whose stored version is behind
  (none stored = 1) has every row of `coin_tags` and `narratives` deleted once, so no answer made under older rules
  is shown; `narrative_spend` is kept (the day's cap survives), one log line gives the counts, and the coins are read
  again under the new rules as they come up. The next start does nothing.
- **Tables**: `narratives (id, title, theme, key, created_at, last_seen_at, retitled)` (`key`: the title folded for the
  near-duplicate check, unique; `retitled` 1 = its title was widened once), `coin_tags (mint, narrative_id, tagged_at, model, asks, had_post, bare)` (`narrative_id`
  NULL = "none"; `bare` 1 = the ask carried neither a description nor a post; `model` `gave-up` for a coin that failed
  alone, which counts for a day), `narrative_spend (day, in_tokens,
  out_tokens, usd, requests)` (`day` a UTC date).
- **Replay tool** (the owner's measurement, by hand; it opens the database read-only and stores nothing but its report):

      node scripts/narrative-replay.mjs --db <DATA_DIR>/spore.sqlite --key-file <path> --out <dir> [--model claude-haiku-5-5] [--hours 24] [--max-coins 1500] [--max-usd 0.50] [--until <unix seconds>] [--also <mint[,mint...]>] [--dry-run]

  It takes the coins created in the last `--hours` (before the newest coin in the file, or before `--until`) that reached the buyers bar, the
  newest `--max-coins` of them in creation order, runs them through the same tagging code (the same instructions, boilerplate stripping, empty-coin guard
  and one-time retitle) with the narratives kept in
  memory, writes `<out>/replay.json` and prints: coins read, requests, tokens, cost, the projected cost a day at that
  rate, the share tagged and "none", the number of narratives, the coins the empty-coin guard stored as "none" and the
  wider titles applied and refused, the 25 largest with up to 12 coin names each, and 20
  random narratives with one coin. `--max-usd` is a hard stop for the whole run, also across a UTC midnight, and a
  request that got no answer (a timeout) stays counted at its worst case. Eight unusable replies in a row end the
  run. `--dry-run` sends nothing (every coin reads "none";
  token figures are rough estimates). `--until <unix seconds>` ends the window at that time instead of at the newest
  coin in the file, so runs over a file that keeps growing read the same coins and can be compared. `--also
  <mint[,mint...]>` (at most 50, may be given more than once) names extra coins that are read after the window's
  coins, in batches of their own, whatever their creation time or buyers, as a coin that shows up on the page later
  would be; one that is not in the file is reported and skipped, one that is among the window's coins is not read
  twice. The report lists where each landed (`also: <name> ($SYM) -> <title or none>`, "not read" when the run
  stopped first; `also` in replay.json). They cost like any coin and count toward `--max-usd`; the tagged and "none"
  counts and shares stay those of the window's coins, and the groups list an extra coin with `also: true`. Also `--min-buyers`, `--per-min` (default 20), `--in-usd-per-m` /
  `--out-usd-per-m`. The key is never printed.
- **Story groups, live** (step 1, recorded, not shown; lib/story-groups-live.mjs, with NARRATIVES=on): a worker thread reruns the rule below once an hour over the last 24 h on its own read-only connection (about 2 s, off the server loop) and maps each narrative to its group, keyed `g:<words>` (a group mostly made of a previous group's narratives keeps its key). At the 5-minute close (lib/attention.mjs) a tagged coin is filed under its subject's `t:` key (subjects/table.json story rows) and its group's `g:` key too, so both get story_buckets rows, starts, phases and calibration snapshots (on top of CALIB_MAX; scripts/attention-calib.mjs leaves t:/g: out). Subject cards on /api/stories do not show that series yet. Every coin with a $1+ buyer in a story also gets a `story_coins` row per bucket (story, subject and group keys, buyers, buy USD, sells, last price, copy key), trimmed after 14 days: the outcome study reads price change, peak and copycats from it. Health: `storyGroups`, `attention.coinRows`.
- **Story groups** (step 0 of automatic grouping, nothing in the product reads it yet): `node scripts/story-groups.mjs --db <sqlite> [--at <ISO>] [--hours 24] [--base-hours 72] [--expect subjects/labels.json] [--table subjects/table.json] [--json]`. Narratives with buyers in the window join when their titles share a distinctive word (not on the NEVER lists or the everyday STOP list) and they share buyers: the median share of each one's wallets also bought by the others is 10% or more (wallets on 25+ coins left out), and the second narrative has 20+ buyers. Checked again after each narrative goes to one group (a story row before a company row, then the group with more buyers). Launches in coin names are reported, never enough alone. On Nov 23-24 (a slim extract of $1+ buys kept in local/data/extracts, since trades are trimmed to 24 h): 11 groups, Jensen 23 of 27 labelled narratives with 1 wrong, Helius 5 of 5, 7 of 13 table story rows found again (GTA 6, Zolana, Riemann, Cat Mario, Shrek and Harry Potter share too few buyers to count as one story); launch-only groups were all unrelated titles.
- **Subject replay** (slice 0 of the subject layer; the Discover cards read the same table through lib/subjects.mjs, see the /api/stories subject blocks): one subject (a named person,
  company, franchise, project or event) is often split over many narratives. By `subjects/table.json`, in the 24 h
  before Nov 24 2026 01:05 UTC the Jensen Huang return was 35 narratives (27 with buyers) and GTA 6 was 77 (33 with
  buyers). The script opens the database read-only and writes nothing:

      node scripts/subject-replay.mjs --db <DATA_DIR>/spore.sqlite [--hours 24] [--at <ISO>] [--min 3] [--json]
      node scripts/subject-replay.mjs --db <DATA_DIR>/spore.sqlite --anchors <table.json> [--expect <labels.json>] [--quiet-share 0.03] [--new-after <id>] [--hours 24] [--at <ISO>] [--json]

  Without `--anchors` it lists candidate words: title words held by `--min` or more narratives with buyers in the
  window, each with its narratives, distinct buyers, shared words and longer variants (gta → gta6); words on the
  built-in `NEVER` lists (standing names like trump and elon, animals, seasons, generic words, platforms) are marked,
  not dropped. With `--anchors` it folds narratives into the table's subjects: a narrative joins a subject that
  `include`s it, else one whose anchor it holds as a whole word and that does not `exclude` it.
  - **Story rows and quiet rows.** A story row's word names one story: a person inside one saga, an event, a fictional
    work, or a meme or coin's own name. A company, brand or product name keeps making unrelated stories (on Nov 23,
    Nvidia had mascot coins, stock chatter and the CEO succession), so its row is `quiet`. A quiet row folds as usual
    but shows as a block only when its distinct buyers reach `quietShare` of the site's (3% by default, `--quiet-share`
    or the table's `quietShare`). A person who simply posts a lot gets no row.
  - **Ties.** When a title holds anchors of two subjects, a story row beats a quiet row, then the longer matched anchor
    wins, then table order. The order never depends on counts, so it cannot flip.
  - **Per subject** it prints:
    - narratives, angles with buyers, and distinct $1+ buyers counted once;
    - share of the site's buyers;
    - whether it would show as a block (2+ angles with buyers, and for a quiet row the share);
    - the checks largest angle ≤ subject ≤ sum of angles, and subject ≤ site.
  - **`--new-after <id>`** lists, for narratives with a higher id (ids grow with time):
    - each subject's new members, to spot wrong joins;
    - new narratives with buyers that joined no subject, to spot misses that need an `include` or a new anchor.
  - **`--expect`** checks labels and exits 2 when one fails:
    - `in`/`out` ids per subject key;
    - `neverAnchors`: words no row may use, whatever its key;
    - `oneSubjectFor`;
    - `none`: ids that must stand alone;
    - `quiet`/`story`: row kinds. Once either is given, every row must have a kind.
    - `absent`: keys that must not exist. It checks keys only; the deleted poster rows are also banned by word in
      `neverAnchors`.
  - **Keys.** A row's key is fixed in the table, so editing its anchors does not rename it. Without one, the key is
    `t:` + the anchors sorted and joined by `-`. Formats are at the head of the script.

## Story attention (lib/attention.mjs)

How much attention a Discover story gets now, as context: never a forecast, and nothing here ranks or rates a coin.
Every live trade of a tracked coin (`model.recordTrade`, never the boot seed and never a gap-fill row: the buckets are
stored, so a seed would count them twice) goes into the open 5-minute bucket (clock-aligned, closed 5 s after it ends,
like the wake-ups) in O(1): its coin's distinct $1+ buyers (the trending rule; a trade without a USD value is $0), buy
USD and sells, and the site-wide distinct buyers (the denominator). A timer looks every 5 s and closes a due bucket in
ONE sliced job (a yield every 64 coins, every write a transaction of at most 200 rows). Only tracked coins are seen:
spawns, coins priced in another asset and parents; SOL-priced roots are not indexed live.

- **Story key** (lib/stories.mjs `storyKey` / `parseStoryKey` / `coinStoryKey`, the same keys as the cards): `"n:<id>"`
  for a narrative, the X post id for a post, the parent mint for a family; `"*"` is the whole site. At the close each
  coin of the bucket is filed by the cards' own precedence: its narrative tag when that narrative is on (2+ of its
  coins, a coin and its copies counting once, had a $1+ buyer in the last 12 buckets, 1 h: the widest card timeframe,
  so the series stays continuous and can hold buckets where a 5m card would not show the narrative; it stays on for 12
  buckets after that stops holding), else its linked post when that post's text is stored and may be
  shown (the post store's own record, read without queueing a fetch, checked at most every 5 min), else its waking
  family (live, not silent) under the family's chosen post when that may be shown, else under the parent mint; else no
  story. The key is fixed at the close (at most 5 min after the trade) and never rewritten: a coin tagged later counts
  under its narrative from then on only, so a narrative's series under-counts its early buying (tags come after 10
  buyers). Bot dust (the cards' rule: "paper" from the coin's market cap and liquidity now; "tiny" from the bucket's
  USD volume per $1+ buyer, where a card uses its timeframe) is in no story; it still counts in the `"*"` row, which is
  every $1+ buyer of every tracked coin.
- **Buckets**: one `story_buckets` row per story with a trade in the bucket (the 2 000 with the most buyers at most) and
  one `"*"` row. A story's `buyers` are the distinct wallets over its coins; `leader_mint` / `leader_buyers` its coin with
  the most; `launches` its coins created in this bucket or the one before, counted once, at the coin's first close
  (metadata and the post link come after the create event); `launches_fast` those created within 60 s of the story's
  post (a post story's own post, a narrative coin's own usable post; a family has none). `flags` 1: the bucket of the
  first live trade the process saw (partial; left out of baselines). A bucket is **seen** when its `"*"` row exists
  with `flags` 0: the bucket open at a shutdown, the buckets of a downtime and the boot bucket are not. Kept 14 days (an
  hourly sliced trim, 2 000 rows a step; the trades trim never touches it).
- **Start** (`story_starts`, written once): a post story at its post's time (`source` "post"), a family at its wake-up's
  start ("wake"; a later wake-up of the same parent moves it forward, the only case), a narrative at its first bucket
  with a buyer ("buyers"); `first_buyers_at` never moves.
- **Normal**: the median, over the story's own rows older than 1 h within the 14 days that had a buyer and are not
  partial, of `buyers / site_buyers`. Empty buckets are left out (with them the median of a sporadic story is 0), and so
  are buckets the server did not see. Read from sqlite in the close job only (one indexed read per story, at most 100
  stories a close, most buyers in the last hour first, again after 30 min), never in a request; the same read gives a
  story new to memory its last hour back (after a restart). A story has a **multiple** only with `first_buyers_at` 6 h
  ago or more, 12+ baseline buckets and 10+ buyers summed over its last 12 buckets, all 12 seen:
  `multiple = (buyers / site_buyers of the last closed bucket) / normal`, 1 dp; otherwise null.
- **Phase**, the first that holds (`last30` / `prev30`: the bucket buyers of the last 6 closed buckets and of the 6
  before, summed; `peak30`: the most of any 6 consecutive buckets, `last30` included): `new` (no multiple; so for about
  an hour after a restart, when the last 12 buckets were not all seen and a hole would read as a drop); `rising`
  (last30 >= 1.25 x prev30, last30 > prev30 and multiple > 1); `peaked` (last30 >= 0.7 x peak30 and last30 < prev30);
  `fading` (last30 <= 0.75 x prev30, or last30 <= 0.5 x peak30); else `steady`. A 25 % fall within 30 % of the peak is
  "peaked". A story with no buyer for 12 buckets is let go from memory (5 000 held at most).
- **Calibration log** (`calib`, not shown anywhere): every close, a snapshot of the 300 stories with the most buyers in
  their last hour (phase, multiple, last bucket's buyers, hour buyers, leader and its price then, the bucket's buy USD),
  only at a close whose last 12 buckets were all seen; the close fills, for snapshots 1 h and 6 h old (300 per horizon
  per close), the story's buyers in the hour(s) after, the leader's last stored price at that time (one indexed read
  each) and `cov_1h` / `cov_6h`: how many buckets of that window were seen (one count per snapshot time). Kept 90 days. Read it with
  `node scripts/attention-calib.mjs --db <DATA_DIR>/spore.sqlite [--days 30] [--json]` (read-only): per phase and band
  of the multiple (none, <1x, 1-2x, 2-4x, 4x+), how many snapshots, how many outcomes were left out because their window
  was not all seen (12 / 72 buckets; a restart or downtime would read as fewer buyers), the median of next-hour buyers over the hour before,
  the share with more, and the leader's price at +1 h / +6 h over its price at the snapshot. Snapshots of one story 5
  minutes apart overlap: n counts snapshots, not independent cases.
- **Coin days** (`coin_days`, not shown yet, never trimmed): per coin per UTC day the high, low and close USD price
  (from priced trades; the newest trade by time closes), buys ($1+), buyers (distinct per 5-minute bucket, summed: a
  wallet in two buckets counts twice), trades and USD volume. Updated in memory per trade and added to sqlite at every
  close as deltas (500 rows a transaction), so a restart loses at most the open bucket's and never counts twice. It
  keeps the all-time high, a 7-day low and "yesterday" after the trades are trimmed.
- **Pre-registered events** (`prereg/events.json`, committed; not under `data/`, which is the runtime folder and ignored
  by git): upcoming dated events written down before their date with their keywords, windows (baseline T-7d..T-2d, pre
  T-24h..T, event T..T+12h, after T+12h..T+36h), metric, comparison and what counts as a hit; the file's `rule` says it
  in full. While an event records (T-14d, for the 2-week comparison, to T+36h) the trade hook adds the $1+ buyers of
  coins whose name or symbol matches (whole words, phrases, name parts; memoized per coin) to `event_buckets`: distinct
  buyers, those of pre-existing coins (created before T-36h) and of new ones (undated counts as new), the coins, and the
  site's $1+ buyers (the denominator). A row is written for every bucket closed while the event records, 0 matching
  buyers included, so the result never needs `story_buckets` (trimmed after 14 days) and a bucket with no row is one the
  recorder did not watch (before the server knew the event, or down).
  `node scripts/event-results.mjs --db <DATA_DIR>/spore.sqlite [--events prereg/events.json] [--json]` (read-only)
  prints each event's result by its rule (HIT / MISS / NOT ENOUGH DATA, OPEN before its after window ends), from
  `event_buckets` alone, so it reads the same on any later day. Recording
  began with this build, so the seeded events have only the days since as comparison. Do not edit an event once its
  window opened: add a new one.
- **Health**: `attention` (open buckets, wallets held, stories held, closes, the last close's CPU and longest slice,
  rows, baselines read, snapshots and outcomes written, coin-day rows, event rows, the events recording, caps hit).

## Root agents (DESIGN §13, phase 0: dry run)

**On the site (DESIGN §13.2).** The API serves only public agents — roots that are Spore launches
(`model.isOurCoin`) and agents the owner runs; a paused agent of a foreign root (the 2026-10-19 seeds)
is never served — and, for each, its wallet and balances, lifetime totals, the coins it launched and
its activity, read from the live ledger `DATA_DIR/agents/ledger.jsonl` (`lib/agents-live/ledger.mjs`:
tailed incrementally by byte offset, malformed lines skipped and counted in `/api/health.agents.ledger`,
the lines of one action folded into one item with a human title and its transaction). Balances come
from the live pass under `AGENTS=live`, else from the RPC on the api lane, cached 60 s per address.
Nothing is written for the site; `AGENTS=off` still serves what is stored.

Every root coin can have an agent that learns what the coin is about and proposes new coins under it.
In this phase an agent **never signs or sends anything and holds no key**: it builds the exact launch
transaction and simulates it. That is enforced in code: `lib/agents/` has no keypair type, signing or
send call (a test scans it), all chain access goes through `readOnlyRpc` (five reads plus
`simulateTransaction`, everything else throws), and the agent wallet and the mint are placeholder PDAs
(off-curve: no private key can exist).

One run (`lib/agents/runner.mjs`): **profile** (`profile.mjs`, built once: summary, 3-8 themes, tone,
avoid, palette; from the language model when `LLM_URL`/`LLM_KEY_FILE`/`LLM_MODEL` are set, else a
deterministic keyword fallback) → **momentum score** (`scorer.mjs`: trades/buys in the last hour, 24 h
trades and volume from `lib/activity.mjs`, children, time since the last proposal; 0-100 with a reason)
→ **gates** (score ≥ `AGENT_MIN_SCORE`, one per root per `AGENT_COOLDOWN_MIN`, ≤ `AGENT_MAX_PER_HOUR`
across agents; only depth-0, non-mayhem roots) → **six ideas** (`designer.mjs`: model ideas topped up by
templates, wordplay on the ticker), filtered (lengths, plain text, no links, `blocklist.mjs` people and
brands, hashed slurs and vulgar words, tickers of the root's children and the 2 000 biggest coins, a
child's name, near-duplicates of the root ticker) and ranked (theme fit, brevity, uniqueness) → **logo**
(`logo.mjs`: SVG from the palette, a motif and stroke-font letters, rasterised by `@resvg/resvg-wasm`,
512×512 PNG in `DATA_DIR/agents/<id>.png`) → **simulation** (`simulate.mjs`: create_v2 under the root +
sharing config with Spore's split for the agent's placeholder, the same instructions as the web's
`buildSpawnTx`, two transactions under a migrated root; the first simulated with the probe wallet paying
the fee and lending the placeholder 0.1 SOL, the second's rent computed) → stored proposal (`proposed`,
or `rejected` when the simulation failed) → SSE `agent { root, proposal }`.

With `AGENTS=dry` the loop runs in-process every `AGENT_TICK_SEC`, one run at a time, on the api RPC
lane; it also announces proposals the CLI wrote. Measured 2026-10-19 on the full-data copy: a run takes
≈ 1.5 s (most of it the simulation's five reads), the first launch transaction is 884-891 B and uses
145-205 k CU, the estimated cost is ≈ 0.0148 SOL (no launch fee).

All JSON; errors are `{ error }` with a 4xx/5xx status; unknown mint → 404. Field-for-field as in
DESIGN §7, plus a few extras that never replace a contract field:

- `GET /api/stats` → `Stats`

- `GET /api/roots?sort=locked|children|new|volume&limit=50&offset=0` → `{ roots, total }` (`new` = most recent child)

- `GET /api/tree/:mint?depth=3&limit=100` → `TreeNode` (children sorted by `lockedUsd`, `limit` per node)

Serving what is stored is never limited; a new job counts against `RATE_HISTNEW` per IP, and a refusal serves what is stored (never a 429)

The page answers for `[from, before)`; `next` is the `before` of the page below it (null: nothing older, the coin's start or no source); `state` `"loading"` (GeckoTerminal is asked for this stretch, or for the stretch between the stored row's top and our first stored trade when retention moved that trade past it, or the chain is being read for the coin's first time over this stretch: nothing to apply, ask the same page again; `no-store`), `"held"` (older GeckoTerminal candles exist but cannot be fetched now: the day's budget, the coin's back calls, the row full, a recent failure, `RATE_HISTNEW`; `from` = `next` = where the stored part starts) or `"done"`; `gecko` / `chain` credit what is in the page. `400` without `history=1`, with `scope=all`, a `before` that is not a positive integer or a `key` other than usd/quote; below the creation bucket `{ candles: [], from, next: null, state: "done" }`. Without the history (`CHART_HISTORY=0`, another resolution, an untracked coin) a page is our stored trades only. Cached `max-age=60` when the page is entirely before our first stored trade, else 5 s. Bounds: one GeckoTerminal call fetches up to 1 000 candles (two pages) and a page queues at most one; 4 of a coin's 16 calls a day are never spent on older pages; 5 000 candles per (coin, res, unit) row, and rows over ~120 KB not asked for 3 days, or past the 300 most recently asked, keep their newest 1 000 (`history.stats.back*` in `/api/health`)
- `GET /api/narrative/:mint` → `{ mint, asOf, members, linked, events: [{ id, url, at, lastAt, postAt, coins, usd24, state, handle, text, top: [{ mint, name, symbol, image, usd24 }] }], earlier, own, under, pending }`: the **posts linked by a family's coins**, as a timeline. Coin creators can put an X post link in a coin's metadata (`twitter`, sometimes `website`); `:mint` is a tracked coin or a mint coins are priced in (a listed asset), and its `members` are its direct tracked children created in the last 72 h or traded in the last 24 h, `linked` of them with a post link. `events`: one event per post that two or more launch addresses among the members link (and whose id gives a time; volume never admits one), **newest first**: `at` is when the first coin linking the post was created, taken from every tracked direct child that links it, also one that is no member any more (so an event's time stays where it is when its first coin goes quiet, and a trade on that coin does not move it); `lastAt` is the last member's creation time, `postAt` the post's own time read from its id (unix s; an event none of whose coins has a creation time stands at `postAt`). Which posts are events, and their `coins`, `usd24` and `top`, come from the members alone. The order is `at`, then the id, nothing else: no score, so the times in the list only go back. **Known limit:** the order is recency and nothing else, and two launch addresses are enough for an event, so the newest lines are whatever posts coin creators chose to link most recently: two addresses that each launch a coin linking a post put it at the top of a parent's timeline, above an event many creators link, and can push older events out of the list by repeating that. Nothing ranks an event by how many creators link it or by what its coins traded. At most 12 are listed (of the 30 newest the server keeps per family); `earlier` counts the events older than the last one the server looked at to fill the list, so it is never a newer event that was left out because X does not show its post (a hidden post newer than that is not counted; posts older than the list are counted without being looked at, so some of them may not be showable). The first 5 listed events ask for their post text at full priority, the ones after them at the fetcher's low priority (refused from half its line and half the day's requests on), so lines a page shows only after "Show more" cannot crowd out first lines. `coins` link the post, `usd24` is those coins' summed 24 h volume (a number about the coins, not about the post), `top` its 3 most traded coins as coin refs, `url` always `https://x.com/i/status/<id>` (rebuilt from the id; the handle in a creator's link is never used: such a link can name anyone). `state`: `"ok"` (`handle` and `text` are the post's, from X's public embed API, plain text of at most 600 characters, `""` for a post of media only or a text with a blocked word), `"wait"` (being fetched, expected within about 40 s), `"idle"` (not fetched now: far back in the line, the day's or this IP's allowance is spent, X is pausing us, or `NARRATIVE_POSTS=0`), `"none"` (X does not show it; only on `own`, such a post is left out of `events` and is not counted in `earlier`); `handle` and `text` are null unless `"ok"`. `own` (a tracked coin only, else null): the coin's own post `{ id, url, at, state, handle, text, siblings, top, parent: { mint, name, symbol } | null }`, `siblings` the other coins under the same parent that link it (null for a coin priced in SOL) and `top` 3 of them. `under`: for a coin with a parent, no post of its own and no `events`, `{ mint, name, symbol, event }` with the parent's newest listed event (an `events` item), else null. `pending`: some state is `"wait"`, ask again (never cached; otherwise 30 s, or 5 s while a post is `"idle"`). The posts are picked by coin creators and not checked, and their authors may have nothing to do with the coins. 400 for an invalid mint; 404 for SOL, an unknown mint, an untracked coin that no coin is priced in, and with `NARRATIVE=0`.
- `GET /api/post-fill?url=<x.com or twitter.com post link>` → `{ id, state, handle, text }`: one X post, for the coin page's "Launch a child" fill (name and ticker suggested from the text, in the browser). Only status links on x.com / twitter.com (the forms `parsePost` accepts, at most 300 characters) are taken, else 400; only the id's digits reach X. `state` as in `/api/narrative` (`"ok"`, `"none"`, `"wait"`, `"idle"`); a post not stored yet is asked for at low priority (never the first half of the post fetcher's line or day, which linked posts keep), on this IP's `RATE_POSTFILL` allowance (not shared with `/api/narrative`) and at most 200 such asks a UTC day server-wide, and the client asks again while `"wait"`; when it is not asked for, `reason` says why (`"busy"`, `"budget"`, `"limit"`, `"retry"`, ...). `text` is `""` for a post with a blocked word; `handle` and `text` are null unless `"ok"`. Never cached. 404 with `NARRATIVE=0` or `NARRATIVE_POSTS=0`. No image: X's embed API gives none.
- `GET /api/discover?tf=1m|5m|30m|1h` (default `5m`; any other value 400) → `{ asOf, bucketS: 300, tf, families: [{ parent: { mint, name, symbol, image, isCoin }, startedAt, state, ratio, peakRatio, buyers5m, trades5m, spark, sparkFrom, baseline, coinsTrading, post, coins, more, hidden, dust, sparkEx, buyersEx5m, bought5mUsd, sold5mUsd, coins5, topShare, topMint, topSymbol, silent, high24 }] }`: the **families waking up**: parents whose existing coins many more wallets are suddenly buying than usual (lib/wakeups.mjs). Why this and not launch counts: in a backtest over Nov 8-19 2026, after a news post the buying landed within 5 minutes on a parent's older children, not on new launches, and the launch count rose only about 30 min later. **The WAKE rule**, per parent (a coin or a listed asset coins are priced in, never SOL), judged on a **trailing 5-minute window** (t − 300, t] (block time, unix s): count the distinct wallets that bought (trade value ≥ $1) any **existing** child in the window (launched more than 30 min before the window starts, `createdAt` < t − 2100, or with no known creation time; **a busy launch only from 2 h**, below). It fires when that count is ≥ 50, ≥ 3 distinct existing coins were bought in the window, and the count is ≥ 5× the parent's trailing mean per clock-aligned 5-minute bucket: the mean over the buckets that ended at or before the window start and were actually observed (the history starts at the first trade the wake-ups saw, of any coin: the boot seed's oldest row of the last 24 h, else the first live trade; at most 288 buckets, 24 h; empty ones count 0), so the bucket the window starts in is not in it. Nothing fires before 6 h (72 such buckets) of history was observed, so a restart never compares the boot seed's first buckets with an empty history (over 27 h of real trades that listed the always-busiest family as "buying 1,273× its normal"); a parent with no trade in the observed history has a baseline of 0. **When it fires:** the window is judged after every $1+ buy of one of the parent's children (as of that buy's time; a late print counts as of the newest buy) and on the 2 s tick for every parent with a buy in its window (as of 5 s ago: buys leave the window, a child crosses the 30-minute line, the baseline moves on at a bucket edge). So a wake-up starts at the buy that makes the window meet the rule, mid-bucket, also when the burst straddles two buckets of which neither has 50 (it used to start only when a fixed bucket closed). Why: a backtest over Nov 15-19 2026 judged the same rule on a trailing window every 15 s and caught 92 % of the bucket rule's alerts a median 105 s earlier (NVDAx on Nov 17: 15:57:15 instead of 16:00, two minutes after the post at 15:55:16); about a quarter of its own alerts had no bucket-rule match, and 1- and 2-minute windows did worse. Judged on every buy, a fire comes a few seconds before that 15 s grid would have seen it (replayed through lib/wakeups.mjs over the same days: a median 7 s), and a window that meets the rule for only a second or two between two grid points fires too: 5 of 115 alerts over Nov 15-19 (about 4 %, 1.4 a day, each right at the threshold: ratio 5.00-5.04 or exactly 50 buyers; one moved that family's next alert out through the 3 h gap), with 110 of the grid's 123 alerts matched. **A busy launch is not existing at 30 minutes.** A coin's buyers are ignored for its first 30 minutes and then all count at once, so a launch that was already heavily bought made its family read "N× its normal" the second it turned 30 minutes old with nothing changed: 22 of 117 wake-ups over Nov 15-19 2026 fired within 2 minutes of such a crossing, the family's buyers were flat against 10 minutes earlier (median 1.10×, against 6.66× for the others) and the lead coin was down 30 % or more an hour later in 76 % of them (50 % for the others). So a coin with 20 or more distinct $1+ buyers in its minutes 15-30 (by the trades' own times) counts as existing only from 2 h of age, in the window and in the buckets alike (it is still listed on cards and in trending). The buyers are counted as they come, per coin, in a set that stops at 20 (one Set add per such buy); the flag is set at the 20th and kept until the coin is 2 h 5 min old (health `wakeups.heldBack`, `heldFlags`, `heldCounting`; the boot seed rebuilds it). It used to be decided at the coin's first buy past the line from the parent's last 15 minutes of buckets: when that buy came a few minutes late the busy minutes had left the view (927 coins flagged where this count has 1,044, and one start in 3.7 days counted such a coin as existing). In the replay the flag took alerts from 115 to 99 and wake-ups whose buyers were flat from 28 % to 18 % (measured with the earlier decision). Its cost: a real burst on a 30 min to 2 h old coin that was already busy starts no wake-up (about 3 cases in 3.7 days, alerted 16 to 131 minutes later); 6 of 106 starts in the replay still came within 2 minutes of a 30-minute crossing (22 of 111 before); the step can reappear at the 2 h line; coins with no known creation time pass both lines untouched. **What was re-tested and left alone** (Nov 20 2026 review): the 50-buyer floor (at 20 / 30 / 40: 67 / 34 / 11 extra alerts that never reached 50 within 3 h, one family each with a coin holding 1.5×, against 37 of 112 for the live rule; the head start at 20 is a median 0 s, p75 95 s, p90 23 min, 18 of 115 alerts 5+ minutes sooner; revisit only if the extra alerts' hit rate nears the live rule's); the 30-minute line (no line: 2.4× the wake-ups at a third of the hit rate; at 2 h: 45 of 120 wake-ups lost and 15 delayed by a median of 33 minutes; it is not free: 43 of 120 wake-ups had 10+ minutes of buying before them that the line hid, 8 of them almost exactly 30 minutes); newest-first order (by ratio and by buyers were within noise). A firing window keeps the parent's current **wake-up** going (it is hot then). A parent without one starts one; it sends the alert (SSE `wake`) only when the parent's last alert is 3 h or more behind, else it is listed again without an alert. **Always-busy families start silently:** for a parent with a baseline of 10 or more buyers per bucket the 24 h mean includes its quiet hours, so 5× the mean is reached several times a day (35 of 115 alerts came from 9 such families, firing at a median 0.62× of their own busiest bucket of the day). Such a start alerts only when its existing-buyer count is at least 0.8× the parent's highest existing-buyer bucket of the last 24 h (`high24`: read from the baseline ring at the fire, the bucket the window starts in left out). Otherwise the wake-up is listed with `silent: true` and the 3 h lock is not used; its alert is sent once, later, the first time a firing window or a closed bucket of that wake-up reaches the same mark (`silent` is false from then; in the replay 6 of 28 silenced starts reached the day's high 2 to 16 minutes later, which would otherwise have been the day's largest burst with no alert). A family with a baseline under 10 is never gated. This is noise control, not a quality filter: the busy alerts it keeps did no better than the ones it holds back. The replay measured the gate at 1.0× the high (about 25 alerts a day instead of 31); 0.8× softens the cliff and was not re-measured (`HIGH_SHARE` in lib/wakeups.mjs). Health `wakeups.silenced`, `caughtUp`, `lastCatchUpS`. A closing bucket starts nothing (one that meets the rule as a whole keeps a wake-up hot). `startedAt`: the fire time (unix s, the buy or tick at which the window first met the rule). **The headline is the trailing window, read when the body is built**, as the rule reads it (it used to be the last closed bucket's, up to 5 min behind the coin rows under it and off by 2× or more in a fifth of 10 s samples). `buyersEx5m`: distinct wallets that bought ($1+) an existing child in the trailing 5 minutes; `baseline`: the trailing mean that window is judged against (1 dp; the last closed bucket's when it cannot be read); `ratio` = `buyersEx5m` over `baseline` (1 dp; a mean under 1 buyer per bucket counts as 1 in a ratio, so a family nobody bought yesterday does not read thousands of times its normal; 0 when nobody bought in the 5 minutes), so the three always agree; `peakRatio` the highest since the start, over the firing window, every closed bucket and every headline served. `state`: `"live"` while the latest complete bucket is ≥ 3× the current trailing mean (or the window fired since that bucket ended), however long ago the wake-up started, `"cooling"` after; the family leaves the list 1 h after it was last hot (such a bucket, or a firing window) or 6 h after `startedAt`, whichever comes first (judged against the mean frozen at the start, a family that grew stayed "live" for a day). `state` goes by complete buckets and the headline by the 5 minutes to now, so a live card can read under 3×. Until Nov 20 2026 live ended 2 h after the start and the drop came 2 h after the last hot bucket: replayed over Nov 15-19 the page then showed 3.89 cooling cards per view, 0.35 of them at 3× or more (one family read "cooling" at 21× for being 2 h 24 min old), and 47 % of a card's listed time came after its last hot bucket; now 1.99 cooling cards, none at 3×+, live cards 1.09 → 1.40, median listed time 231 → 132 min. The cost: an empty page 4.6 % of the time (1.1 % before), about one more alert a day, and a family that leaves and comes back inside 3 h is listed again without an alert. A gap in the stored trades (the server was down) reads as quiet buckets and lowers a baseline until it rolls out of the 24 h. `buyers5m`: distinct wallets that bought ($1+) any of its children, existing and new, in the trailing 5 minutes; `coinsTrading`: children with a $1+ buy in them (the window holds buys only); `trades5m`: trades of all its children in the latest complete bucket. `sparkEx`: 24 counts of existing-child buyers per bucket for the last 2 h, oldest first, the last one the latest complete bucket: the same population as `baseline` and `ratio`, so this is the line to draw against the baseline (its last point over the baseline is that bucket's ratio). `spark`: the same 24 buckets counting every child's buyers, new launches included (drawn against the baseline it read as a multiple the ratio never said: one always-launching family showed 536 buyers over a band at 64 beside "0.9× its normal"); `sparkFrom`: the start (unix s) of the first of those 24 buckets. `coins5`: how many of its coins (creator-fact coins apart) have 5 or more distinct $1+ buyers in the trailing 5 minutes; `topShare`: the most-bought coin's buyers over `buyers5m` (0-1, 2 dp, null when nobody bought); `topMint` / `topSymbol`: that coin (the first of `coins` unless it is dust). Per build, from the same buyers the rows show, because the 3-coin condition is nominal (in 75 of 113 wake-ups one coin had 70 %+ of the buyers) and a label frozen at the start was wrong on a quarter of cards 15 minutes later. They describe the buying; a family-wide wake-up is not ranked above a one-coin one (the outcome gap between them was only the number of coins). `bought5mUsd` / `sold5mUsd`: USD bought and sold on its existing children (the rule's population, creator-fact coins included) in the trailing 5 minutes, 2 dp, summed over the wake-up's coins: those bought in the firing window, those traded since, and those that only traded (a sale, or a buy under $1) in the two buckets the firing window overlaps, so a coin sold just before the start is in the figure from the first build. A fact per build: the median firing window has 80 cents sold per dollar bought and the sign flips within 5 minutes for half of them. Not a gate and not a warning: silencing alerts on it was tested and showed no dose-response. `silent`: this wake-up started without an alert under the always-busy gate and has not reached its mark yet; `high24`: the parent's highest existing-buyer bucket of the 24 h before the start. A bucket is complete 5 s after it ends (block times trail the clock), or as soon as the parent's next trade is in a later bucket. `coins`: at most 6 of the children traded since the start (the children bought for $1+ in the firing window, so also those bought only in the bucket before the fire, then every child traded after) that somebody bought for $1+ in the **trailing 5 minutes** (a coin nobody is buying now is not listed) and that are not dust (a known `mcapUsd` under $1,000), most such buyers first, then USD volume since the start, then the mint (at most 64 looked at), as **coin rows** (below, over the asked `tf`) plus `copyOf`: `existing` = created before `startedAt` − 1800 or unknown; `mcapUsd` from the coin's live USD price, else (a coin under a stock/asset parent or a newer coin parent, which the model prices in its parent only) the newest stored trade's USD price (one indexed read per coin per build), null when neither exists; `sinceStart` (existing coins only) = its price now over its price at `startedAt` (its last trade at or before it, else its first trade after), in USD when both have one, else in the parent, 2 dp, null without a stored trade; always null for a new coin (measured from its first trade it would count its own launch buy; the web shows "new"); `buyers5m`: that coin's distinct $1+ buyers in the trailing 5 minutes (the same trailing 5 minutes as the family's `buyers5m`, read from the row snapshot, up to 5 s apart); `copyOf` (a new coin that links an X post, else null): how many earlier children of the parent link the same post (5 means it is the 6th; counted over the linked-post members, lib/narrative.mjs, null with `NARRATIVE=0`). `more`: other children (not left out below) with a $1+ buy in the trailing 5 minutes and not listed. `dust`: children looked at and left out as dust. Rows, `more`, `hidden` and `dust` all count coins with a $1+ buy in the trailing 5 minutes, the basis of `coinsTrading`, so they add up to it (snapshot and window are read up to 5 s apart); `more` and `hidden` used to count any trade, a sale too, and a card read "3 coins trading" over 3 rows and "5 more trading". Coins whose creator did one of three things the backtest found on coins that went to nothing are **left out** and counted in `hidden` (those with a $1+ buy in the trailing 5 minutes, as `more` counts; it used to count every one traded since the start beside two 5-minute counts): the launcher sold ≥ 90 % of its own buy within 10 min of launch, launched 10 or more coins (under any parent) in the hour before, or launched the same ticker under the same parent before (a relaunch). The "sold" fact is recorded per coin from the trades while the coin is under 10 min old (its launcher's buys and sells summed, O(1) per trade) and written to sqlite (`launch_flow`) once that window closed, because the per-mint trim of `trades` deletes a busy coin's launch rows within a day. The same window records the sniper share (`launch_flow.sniped`, the coin row's `safety.sniperPct`): base units wallets other than the launcher bought in the creation slot or the first 3 s; launch windows are kept for every tracked coin, a SOL root's too (`/api/trending` lists roots). A window first seen more than 30 s after the launch (a restart, or the boot seed's 24 h cutting through it) may lack the launcher's buy and is not written. Without a record, the stored trades decide only while they still reach back to the launch (its oldest stored trade within 30 s of it); otherwise the fact is **unknown**: the coin is not left out, the fact is asked again after 10 min, and health `wakeups.factsUnknown` counts such coins. The other two facts come from the coin index. They are a filter, not a verdict on the coins listed. `post`: one X post linked by 2 or more of the children traded since the start, chosen in two steps. First a post made between 60 min before `startedAt` and 5 min after it (by its id's time): most links first, then newest. - `GET /api/pnl/:wallet?since=<unix seconds>` → `{ ok, wallet, at, since, history: { state: "queued" | "running" | "done" | "failed" | "off" | "full", scanned, total, cut, unread, since, trackedAt, gap }, trades, coins: [{ mint, coin: { name, symbol, image }, quoteMint, quoteSymbol, quoteDecimals, baseDecimals, boughtBase, boughtQuote, soldBase, soldQuote, realizedQuote, costQuote, heldBase, partial, buys, sells, firstAt, lastAt, realizedUsdNow, costUsdNow }], totals: { realizedUsdNow, costUsdNow, unpriced } }`: what the wallet bought and sold per coin and its profit, for the Portfolio page (`lib/pnl-tracker.mjs`, maths in `lib/pnl.mjs`). The first request makes the wallet **tracked**: from then on every trade of it the indexer stores is also kept in its own table (`wallet_trades`, not trimmed with the per-mint trade history), and its newest `PNL_BACKFILL_TX` transactions are read from the chain once, in the background; the answer never waits for that and `history` says how far it is (`scanned` of `total` transactions, `unread`: transactions that could not be read after 3 tries, or whose trades neither the log nor the inner instructions gave whole (see below; the count goes down when one is read later), `cut`: history is missing because a cap was reached (`PNL_BACKFILL_TX`, `PNL_MAX_TRADES`, `PNL_MAX_ROWS`), `since`: the block time of the oldest transaction read so far, `gap`: a unix time when trades since then may be missing because the server was down, null otherwise, `state: "failed"`: the listing failed or the endpoint stopped answering (five transactions in a row; the scan stops where it had stored and nothing is counted unread) and a later request tries again after 10 min, doubling per failure up to 6 h, `state: "full"`: the wallet is not tracked because the set is full, with `trackedAt: null` and no coins). Amounts are strings in smallest units: `*Base` in the coin's (`baseDecimals`), `*Quote` in the coin's quote (`quoteMint` null = SOL in lamports, else the parent's units, `quoteDecimals`), and a trade's quote amount is what the wallet paid (a buy) or received (a sell) with the venue's fees: pump-amm events name it (`user_quote_amount_in` / `_out`), a curve trade is its amount plus (buy) or less (sell) the event's `fee` and `creator_fee` (not compared with on-chain balances; the network fee and tips are not counted). Average cost: a sell realizes its proceeds less the position's cost in proportion (`realizedQuote`, signed); `costQuote` is the cost of `heldBase`, the base still held according to the trades. A sell of more than the recorded buys (tokens transferred in, or history that was cut) realizes only the explained part and sets `partial`. With `since`, the sums, the counts and `realizedQuote` cover the trades at or after it, while the cost basis is built from the whole stored history (`heldBase`, `costQuote`, `partial`, `firstAt`, `lastAt` are not windowed); a coin without a trade in the window is listed only while a position is held. `realizedUsdNow` / `costUsdNow` are those quote amounts at the quote's price NOW (the SOL price, or the parent coin's current price; there are no historical prices), null when the quote has no price; `totals` sums the priced coins and counts the others in `unpriced`. Trades are applied in chain order: time, slot, then the order of the wallet's transactions inside the slot (from the signature listing for scanned history, arrival order for live trades), so a buy and a sell of one slot are not swapped. `since` is rounded down to a whole minute (the body's `since` says which). Reads only the wallet's own rows by index, in slices of 1 000 per event-loop turn; one body per wallet and `since` is kept 10 s (2 s while the history is being read), at most 4 windows per wallet, 500 wallets and 50 000 coin entries in all, and dropped by a new trade of the wallet. 60 per minute per IP (`RATE_PNL`, shared with `/api/activity`) and 20 new wallets per hour per IP (`RATE_PNLNEW`, 429); 400 on a malformed wallet or `since`; a store that cannot be read answers 200 with `ok: false` and empty lists. Not covered: tokens received or sent by plain transfer are not trades, trades of coins the index does not track are ignored, trades older than the cap are missing (`cut`), a transaction still counted in `unread` after its retries is missing, and a live trade the streams did not deliver while the server was up is missing without a flag. Trades made while the server was down are read by a catch-up when the wallet is next asked for (`gap` until then). **Cut logs.** A node cuts a long log (`Log truncated`, common for routed swaps), and the trade can sit behind the cut. The pump curve and pump-amm programs emit every event twice: as a `Program data:` log line and as an inner instruction to themselves (Anchor `emit_cpi`: the instruction data is the 8-byte tag `e445a52e51cb9a1d`, then the event's discriminator and body, the very bytes of the log line; compared on mainnet 2026-11-16: 28 transactions of both programs, legacy and versioned, with and without address-table keys, the 9 with tracked events byte-identical and in the same order on both paths). So when a scanned transaction's log is cut, missing, or holds an event that does not decode, its events are read from `meta.innerInstructions` instead (`lib/decode.mjs` `eventsInInner`; program ids through the static keys and then the loaded address-table keys), numbered exactly as the log numbers them, so the part of a cut log the live stream already stored is the same row and nothing is stored twice. The inner instructions are trusted only when they hold at least as many events as the log showed; a transaction neither path reads whole stays `unread`. The live streams themselves only have the log, and a cut log does not say whose transaction it is. So the indexer hands the signature of every cut log to the tracker (`onCutLog`: one Map write, the newest 20 000 kept in memory), and a request for a tracked wallet, at most once a minute and only when a log was cut since its last check, lists that wallet's transactions since the check (one `getSignaturesForAddress`) and reads those among them that were cut, like a scan (inner instructions, the same rows, `unread` and its retries when one does not read). A live trade behind a cut is therefore missing until the wallet is next asked for, about a minute on an open page. When so many logs were cut since a wallet's last check that signatures were dropped from the set, every transaction of the wallet since that check is read instead (capped like a catch-up; more sets `cut`). The set is not kept across a restart: the catch-up after a downtime covers that. **Unread transactions are read again.** Each is remembered (`pnl_unread`: at most 200 per wallet and 100 000 in all; beyond that they are only counted) and read again in the background when no scan waits, through the same throttle (`PNL_BACKFILL_RPS`) and daily budget (`PNL_BACKFILL_DAILY`): 2 minutes after it was stored, then after 4, 8, 16 and 32 minutes (5 tries, each with the scan's own 3 attempts). A try the endpoint did not answer at all (every attempt threw: the node is down or rate-limits) is not one of the five: the transaction waits again, doubling up to 6 h, the other unread ones wait 30 s like the scans in an outage, and only 20 such tries in a row (over three days) give it up. One that reads while the table is at `PNL_MAX_ROWS` is not stored: it leaves `unread` and sets `cut`. One that is read gives its trades (placed where the scan would have put them) and takes one off `history.unread`; one given up after the fifth try stays stored and counted, a later scan or catch-up that meets it does not count it twice and clears it if it can read it then. Wallets that counted unread transactions before these were remembered have nothing stored to try: once, at the first start after the update, each such wallet's history is queued to be read again from its newest transaction (`state` goes back to `queued`, `unread` to 0; rows already stored are kept, `INSERT OR IGNORE`), most recently asked-for first within `PNL_MAX_QUEUE`, the others when they are next asked for. A wallet already at `PNL_MAX_TRADES` is left as it is (a second scan would read nothing), and when a row cap stops a second scan the wallet gets the count it had back (kept in `kv` `pnlUnreadWas` until then) together with `cut`. `/api/health` `pnl`: `unreadStored`, `unreadDueMs`, `unreadTries`, `unreadRead`, `unreadGivenUp`, `unreadErrors` (tries the endpoint did not answer), `txInner` (transactions read from inner instructions), `rescans`, `seriesBuilds`, `cuts` (signatures of cut live logs held), `cutLogs`, `cutChecks`, `cutTx` (transactions read by those checks).

## Partner API (/v1, DESIGN §12)

Read-only data for other trading terminals, versioned under `/v1` (`lib/v1.mjs`, OpenAPI in
`lib/openapi.mjs`, keys in `lib/apikeys.mjs`). Only GET routes exist; any other method is 405.

- `GET /v1/coin/:mint/family` → `{ mint, name, symbol, image, depth, quoteMint, quoteSymbol, root, parent, ancestors, children: { count, top }, descendants, lockedUsd, mcapUsd, change24h, trades1h, launchedOnSpore, links }`: any pump.fun mint (live lookup on the api RPC lane when not indexed; 404 when it is not a pump coin, 503 when the lookup fails); `top` = up to 20 children by locked value; `change24h` in percent against the last trade at or before 24 h ago (null without trades); cached 5 s per mint.
- `GET /v1/tree/:mint` → `{ root, nodes: [{ ...MapCoin, parentMint }], total }`: the whole tree containing the mint, root first, breadth-first, siblings by locked value; cached 10 s per root.
- `GET /v1/map[?since=<ms>]` and `GET /v1/heat`: the `/api/map?scope=all&limit=all` and `/api/map/heat` bodies from the same caches (the map bytes rewritten once per build so images are absolute; `since` rounded down to the second).
- `GET /v1/agents`, `GET /v1/agents/:root` and `GET /v1/agents/coin/:mint`: the `/api/agents` bodies with absolute image URLs (root images, launched coins and logos on `PUBLIC_URL`); `agent` is also an opt-in `/v1/stream` type.
- `GET /v1/stream?types=pair,trade,heat,stats[,mapdelta,coin][&mint=<coin>]`: the hub's events (the hub has a `subscribe` hook for in-process listeners), filtered by type and by the tree of `mint` (root resolved per event), `heat` rows derived per trade, absolute images, `retry: 3000`, heartbeat every 25 s, backpressure cut at 256 KB.
- `GET /v1/openapi.json`: the OpenAPI 3.1 document (tests check that every route is listed and every `$ref` resolves).

Every image is absolute on `PUBLIC_URL`. CORS is `*` (GET/OPTIONS, `X-API-Key`, no credentials; preflights
answered before auth); `/api` keeps its allowlist. Family/tree/map/heat send `public, max-age=5, s-maxage=10`
+ ETag/304 so a CDN absorbs polling; the stream and errors are `no-store`.

**Tiers.** No key = public: `V1_RATE_PUBLIC` requests/min per client IP, `V1_STREAMS_PUBLIC` streams per IP.
`X-API-Key: spk_<32 base58>` = partner: `V1_RATE_PARTNER`/min and `V1_STREAMS_PARTNER` streams per key
(`?key=` only on `/v1/stream`, a 400 elsewhere). Invalid or revoked key → 401 (charged to the IP's public
budget). Headers: `X-Spore-Tier`, `X-RateLimit-Limit/Remaining/Reset/Policy`; 429 carries `Retry-After`.
Keys are stored as sha256 only (`api_keys`); a verified key is cached 15 s, so a revocation lands within 15 s;
`requests` / `last_used_at` are written in one transaction every 30 s and at shutdown. `/api/health.v1`
reports open streams and key counters.

It opens `DATA_DIR/spore.sqlite` (`--data <dir>` overrides) next to the running server and refuses a missing
file. The server's connection waits up to 2 s for a write lock (`busy_timeout`) so the CLI never makes a
server write fail.

**Embeds.** `/embed` and `/embed/*` serve index.html with `frame-ancestors *` and no `X-Frame-Options`
(`isEmbedPath` in lib/http.mjs); every other path keeps `frame-ancestors 'none'` + `X-Frame-Options: DENY`.

## Hardening (lib/http.mjs, lib/validate.mjs, lib/net.mjs)

- Headers on every response: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (not on the `/embed/*` pages), `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, a closed CSP for JSON (`default-src 'none'; frame-ancestors 'none'`), HSTS when the request came over TLS. `index.html` gets the SPA CSP (`default-src 'self'`, connect/img to self + `PAGES_DOMAIN`, Google Fonts, Solflare's iframe and same-origin frames (`frame-src 'self'`, so /docs/api can preview the `/embed/*` widgets), `frame-ancestors 'none'`) with a per-request nonce substituted into `__CSP_NONCE__` so one inline theme snippet may exist; nothing else inline.
- Bodies: 16 KB JSON everywhere, 3 MB on `/api/upload` → `413 { error }`.
- Rate limits per IP with `X-RateLimit-Limit/Remaining/Reset/Policy`, `429 { error, retryAfter }` + `Retry-After`. An upload rejected by validation (or by a daily quota) refunds its attempt.
- SSE: new `/api/events` connections are rate-limited per IP, capped per IP and in total (`SSE_*`), and a client that stops reading is destroyed once 256 KB are buffered for it instead of growing the heap.
- RPC: four lanes (indexer / API lookups / browser proxy / wallet history scans) with their own token buckets and 429 pauses; request-driven lookups remember per mint for a minute whether a coin exists, eligibility caches its chain reads per mint (the creator only changes the split math), on-demand coins nobody spawned under live in memory only and are evicted after 10 idle minutes, and the API-view table is pruned every tick.
- Compression: gzip/brotli from `node:zlib` for text/JSON bodies ≥ 1 KB (sync for one-shot responses, streamed for static files); never for the SSE stream.
- Caching: weak ETags + `public, max-age=3–10, stale-while-revalidate` on feed/roots/map/tree/coin/stats/candles (304 on `If-None-Match`); `/m/*` and `/assets/*` immutable; `index.html` no-cache; everything else `no-store`.
- Upload validation: name/description plain text (no `<>`, control or invisible characters, caps 32/400), ticker `[A-Za-z0-9]{1,13}`, socials as handles or x.com/t.me links, website http(s); image data URL ≤ 2 MB whose magic bytes match the declared png/jpeg/gif/webp (SVG never), JPEG APP1/APP13 and PNG text/EXIF chunks stripped before the file is written. A wrangler failure is `502 { error, retryAfter: 30, hint }`; the files stay on disk for the next deploy.
- Outbound fetches (metadata JSON, images): hostnames are resolved and refused when any address is private/loopback/link-local, IPv4-compatible, 6to4/NAT64-embedding a private address, Teredo, ULA or documentation space (`lib/net.mjs`); the TLS connection is then **pinned to the vetted address** (`pinnedFetch` over `node:https` with a fixed `lookup`, SNI and certificate checks on the real hostname), so a rebinding resolver cannot redirect a later fetch; redirects are followed manually with the allowlist and the pin re-done per hop, bodies are size- and time-bounded; proxied images are served with the sniffed type. The image allowlist names the IPFS subdomain gateways explicitly (`<cid>.ipfs.dweb.link` etc., never a `.ipfs.` substring) and refuses any explicit port.
- Logging: `http: GET /api/feed 200 3.2ms 1842B 203.0.113.9` for every error, every request over 1 s and a `LOG_SAMPLE` fraction of the rest; the RPC key is redacted.
- Shutdown: SIGTERM/SIGINT stop the indexer, end SSE streams, let in-flight requests finish, checkpoint and close sqlite, exit within 8 s.
- Backups: `scripts/backup.mjs` copies the sqlite file online (backup API + integrity check), see `../DEPLOY.md`.

Extra fields on `Coin`: `quoteDecimals` (to format `lockedQuote`), `curve`, `mayhem`, `tracked`, `ours`, `oursPending`, `feePaid`, `otherChildren`.
`totalSupply` and `lockedQuote` are raw on-chain integers as strings; use `decimals` / `quoteDecimals`.
`root` and `parent` are `null` on a depth-0 coin.

In production the server also serves `../web/dist` with an SPA fallback for every path outside `/api` and `/v1`.
